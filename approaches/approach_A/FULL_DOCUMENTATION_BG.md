## 1. Основни понятия (за читатели без опит с роботика)

### 1.1 Какво е роботна ръка?

Роботната ръка е механична конструкция, която имитира движенията на човешка ръка.
Тя се състои от **звена** (links) — твърди части, свързани помежду си чрез **стави**
(joints). Всяка става позволява въртене или плъзгане.

```
ОСНОВА
  │
  ├── Звено 1 (base → рамо)         ← 173.9 mm
  │       ↕ Става j1 (завъртане ляво/дясно)
  ├── Звено 2 (рамо)                ← 135 mm
  │       ↕ Става j2 (наклон напред/назад)
  ├── Звено 3 (лакът)               ← 120 mm
  │       ↕ Става j3 (наклон напред/назад)
  ├── Звено 4 (китка 1)             ← 95 mm
  │       ↕ Става j4 (наклон)
  ├── Звено 5 (китка 2)             ← 65.5 mm
  │       ↕ Става j5 (завъртане)
  ├── Звено 6 (крайна точка)
  │       ↕ Става j6 (завъртане)
  └── Захват (gripper)              ← ~144 mm до центъра на захват
```

### 1.2 Ставни ъгли

Всяка ставна позиция се описва с един ъгъл, измерен в **радиани** (rad).

```
Преобразуване: ъгъл [°] = ъгъл [rad] × (180 / π)

Примери:
  0.0 rad  =   0°   (неутрална позиция)
  1.57 rad =  90°   (π/2)
  3.14 rad = 180°   (π)
 -1.57 rad = -90°
```

### 1.3 Координатна система

Използва се **дясна ортогонална координатна система**:

```
        Z (нагоре)
        │
        │
        └───── Y (наляво)
       /
      X (напред)
```

Началото (0, 0, 0) е в центъра на основата на робота.
Всички позиции в симулацията се измерват спрямо тази точка, в метри.

### 1.4 Какво е ROS2?

**ROS2 (Robot Operating System 2)** е рамка за разработка на роботни системи.
Тя не е операционна система, а набор от библиотеки и инструменти за:
- Комуникация между компоненти чрез **топици** (topics) — канали за съобщения
- Стартиране на множество програми едновременно (**launch файлове**)
- Стандартизирани формати на съобщения (JointTrajectory, JointState и др.)

```
Аналогия: ROS2 е като електрическата мрежа в сграда.
Различните стаи (програми) се "включват" в мрежата и комуникират
помежду си стандартизирано.
```

### 1.5 Какво е Gazebo?

**Gazebo** е симулатор на физична среда. Той симулира:
- Гравитация и сблъсъци между обекти
- Сензори (камери, лидари, ставни енкодери)
- Задвижването на роботни стави

В тази работа се използва **Gazebo Harmonic (gz-sim 8.x)**.

### 1.6 Какво е ros2_control?

**ros2_control** е система за управление на хардуер/симулация в реално време.
Тя свързва ROS2 с реалния или симулирания робот.

```
ROS2 команда → ros2_control → Gazebo ставни задвижвания
ROS2 топик   ← ros2_control ← Gazebo ставни енкодери
```

При напълно изпъната ръка в хоризонтална посока:
```
Обсег ≈ звено2 + звено3 + звено4 + звено5 + захват

```

Адаптивният захват има 2 пръста, управлявани от 1 мотор (`gripper_controller`).

```
Команда:  0.0  rad → пълно отваряне
Команда: -1.0  rad → пълно затваряне  (ограничение: -1.11 rad = -63.6°)
```

Захватът получава команди по топик:
`/gripper_action_controller/commands` (тип: `Float64MultiArray`)

        ┌──────┐
        │      │  60 mm
        │      │
        └──────┘
          40 mm

Изглед отгоре:
        ┌──────────┐

### 3.2 Начална позиция на обекта

| Ос | Стойност | Описание |
|----|---------|---------|
| X | 0.2620 m (26.2 cm) | Пред основата на робота |
| Y | -0.0842 m (-8.42 cm) | Малко вдясно от оста |
| Z | 0.0300 m (3.0 cm) | Центърът на обекта (полу-височина) |

```
Изчисление на позицията спрямо пода:
  Дъно на обекта = Z_center - половин_височина = 0.030 - 0.030 = 0.000 m (на пода)
  Горен ръб     = Z_center + половин_височина = 0.030 + 0.030 = 0.060 m
```

```
Разстояние от основата на робота до центъра на обекта:
  d = √(X² + Y²) = √(0.262² + 0.0842²) = √(0.0686 + 0.0071) = √0.0757 ≈ 0.275 m (27.5 cm)
```

### 3.3 Фази на задачата

```
ФАЗА 1: HOME

ФАЗА 2: GRIPPER_READY

ФАЗА 3: PRE_GRASP

ФАЗА 4: GRASP

ФАЗА 5: ЗАТВАРЯНЕ НА ЗАХВАТА

ФАЗА 6: LIFT
  Ръката повдига обекта нагоре.

ФАЗА 7: HOME

```

## 4. Метод: Твърдо кодирани ставни ъгли

### 4.1 Основна идея

При Подход A позициите на робота се дефинират директно като числа — 6 ставни ъгъла
за всяка поза. Тези числа са намерени **ръчно**, чрез наблюдение на симулацията
и итеративно коригиране.

```
Аналогия: Представете си, че управлявате кукла марионетка с 6 конеца.
Дърпате всеки конец с различна сила, докато куклата застане на желаното място.
Записвате колко сте дръпнали всеки конец. При следващото изпълнение
повтаряте точно същото.
```

### 4.2 Инструментът: rqt Joint Trajectory Controller

**rqt** е графичен инструмент на ROS2. Приставката "Joint Trajectory Controller"
показва плъзгачи за всяка става и позволява ръчно задаване на позиции.

```
[SCREENSHOT: A1_rqt_sliders.png]
Описание: rqt панел с 6 плъзгача за ставите. Всеки плъзгач се движи
в границите на ставния лимит. Промяната на плъзгача веднага изпраща
команда към контролера и роботът се движи в Gazebo.
```

**Стъпки за работа с rqt:**

1. Стартиране:
   ```bash
   rqt
   ```

2. Зареждане на приставката:
   ```
   Plugins → Robot Tools → Joint Trajectory Controller
   ```

3. Свързване с контролера:
   ```
   Controller manager namespace: /controller_manager
   Controller: arm_controller
   Натиснете "Enable"
   ```

4. Прочитане на текущите ъгли:
   ```bash
   ros2 topic echo /joint_states --once
   ```

```

показващ масива name[] и position[].
```

### 4.3 Процес на намиране на точките

#### HOME — намиране

HOME е позицията, в която роботът стои изправен. Всички стави са близо до нула.
Тя се задава автоматично при стартиране чрез скрипта `set_home_pose.py`.

```
Стойности: [0.0004, 0.0042, -0.0228, 0.0045, 0.0527, 0.0077]
Итерации: 1 — почти нулеви стойности, само малки корекции за изравняване
```

```
[SCREENSHOT: A3_gz_home.png]
Описание: Gazebo — роботът в изправена HOME позиция. Всички стави близо
до нула. Ръката е насочена нагоре.
```

#### GRIPPER_READY — намиране

Целта е j5 да е π/2, за да се насочат пръстите надолу.

```
Изчисление:
  π/2 = 1.5708 rad = 90°

  Намерена стойност: j5 = 1.5567 rad ≈ 89.2°
  (малка разлика поради механична структура на ставата)
```

```
Стойности: [0.0, -0.0006, -0.0856, 0.0226, 1.5567, 0.0]
Итерации: 2 — основната корекция е на j5; j3 получи малко отместване
           за да избегне конфликт с основата при следващото движение
```

#### PRE_GRASP — намиране (4 итерации)

Целта е захватът да е точно над обекта, на 9 cm просвет.

```
Целева позиция на крайния ефектор:
  X = 0.262 m (над обекта)
  Y = -0.084 m (над обекта)
  Z = 0.120 m (30 mm центъра на обекта + 90 mm просвет)

Итерация 1: j2=-0.65, j3=-0.65 → захватът е твърде далеч
Итерация 2: j2=-0.72, j3=-0.72 → по-близо, но малко встрани
Итерация 3: j2=-0.70, j3=-0.72 → добре по X, но Y не е точно
Итерация 4: j2=-0.705, j3=-0.7237 → приемливо над обекта ✓

Намерени стойности: [0.0, -0.705, -0.7237, -0.169, 1.5772, 0.0]
```

```
Ролята на j4 = -0.169 rad:
  Когато j2 и j3 се огъват, крайният ефектор се накланя напред.
  j4 компенсира това, за да остане захватът хоризонтален (перпендикулярен
  на гравитацията — за захващане отгоре надолу).

  Интуиция: j2+j3 "клякат" напред, j4 "изправя" китката обратно.
```

```
[SCREENSHOT: A4_gz_pre_grasp.png]
Описание: Gazebo — ръката над обекта, захватът хоризонтален, видим просвет
между пръстите и горния ръб на обекта (~9 cm).
```

#### GRASP — намиране (6 итерации)

Целта е пръстите на захвата да са на нивото на обекта.

```
Изчисление на целевата Z-координата на захвата:
  Долен ръб на обекта: 0.000 m
  Горен ръб:           0.060 m
  Оптимална Z:         0.030 + 0.015 = 0.045 m
  (центърът на обекта + 15 mm нагоре — за да не ударят пръстите пода)

Итерации:
  1: j2=-0.75, j3=-0.75 → захватът е твърде висок (не достига)
  2: j2=-0.78, j3=-0.78 → по-ниско, но ъгълът на захвата е неправилен
  3: j2=-0.80, j3=-0.80 → почти добре
  4: j2=-0.81, j3=-0.83 → различни стойности за прецизен ъгъл
  5: j2=-0.815, j3=-0.834 → пръстите са около обекта ✓
  6: потвърждение след затваряне → ✓

Намерени стойности: [0.0, -0.815, -0.834, -0.169, 1.577, 0.0]
```

```
Защо j2 ≠ j3?
  Поради различните дължини на звената и техните ъглови отмествания в URDF,
  симетричните стойности на j2 и j3 не водят до симетрично движение на
  крайния ефектор. Необходима е леко асиметрична корекция.
```

Описание: Gazebo — пръстите на захвата обхващат обекта. Захватът е
хоризонтален, обектът е между пръстите.
```

```

Описание: Gazebo — роботът е повдигнал обекта нагоре. Обектът се вижда
удържан от захвата.

## 5. Архитектура на управлението

### 5.1 Топологична схема

```
┌─────────────────────────────────────────────────────┐
│                   pick_place.py                      │
│                                                      │
│  HOME, PRE_GRASP, GRASP → JointTrajectory msg       │
│  OPEN/CLOSE             → Float64MultiArray msg     │
│  /joint_states          ← обратна връзка            │
└──────────┬──────────────────────┬───────────────────┘
           │                      │
           ▼                      ▼
┌─────────────────┐   ┌─────────────────────────────┐
│  arm_controller │   │  gripper_action_controller  │
│  (JointTraj.)   │   │  (JointGroupPosition)       │
└────────┬────────┘   └─────────────┬───────────────┘
         │                          │
         ▼                          ▼
┌─────────────────────────────────────────────────────┐
│           ros2_control / controller_manager         │
│           Честота на обновяване: 100 Hz             │
└──────────────────────┬──────────────────────────────┘
                       │
                       ▼
┌─────────────────────────────────────────────────────┐
│              Gazebo Harmonic                        │
│         (физична симулация на робота)               │
└─────────────────────────────────────────────────────┘
```

### 5.2 Формат на командата

```python
# Команда за движение на ръката
msg = JointTrajectory()
msg.joint_names = ['joint2_to_joint1', 'joint3_to_joint2', ...]
pt = JointTrajectoryPoint()
pt.positions = [j1, j2, j3, j4, j5, j6]   # в радиани
pt.time_from_start = Duration(sec=5)        # 5 секунди за движение
msg.points = [pt]
# → публикуване на /arm_controller/joint_trajectory
```

### 5.3 Проверка за достигане на целта

```python
# Скриптът НЕ просто чака N секунди.
# Той активно проверява дали ставите са стигнали целта:

TOLERANCE = 0.08  # рад ≈ 4.6°

def _at_target(self, target):
    for joint, t in zip(ARM_JOINTS, target):
        current = self._joint_pos.get(joint)
        if abs(current - t) > TOLERANCE:
            return False   # не е достигната целта
    return True            # всички стави са в рамките на допустимото
```

```
Защо 0.08 rad?
  Контролерът използва мек стоп — ставите се приближават до целта
  асимптотично и никога не достигат точно 0.0 грешка. 0.08 rad (4.6°)
  е емпирично избрана стойност, при която роботът е достатъчно близо
  до позицията за безопасно продължаване.
```

## 7. Открити проблеми, причини и решения

### Проблем 1: Захватът се разтваря преди повдигане

**Симптом:** Непосредствено преди командата за движение нагоре, захватът
се разтваря за кратко и обектът пада.

**Причина:** `joint_trajectory_controller` изпраща нова траектория на ръката.
Вътрешно контролерът прекъсва текущата команда на захвата и задава референтно
нулево положение за кратък момент.

**Решение:**
```python
self._grip(GRIPPER_CLOSED)
self._move('grasp', GRASP, sec=2)   # задържа позиция след захват
self._wait(1.0)
self._grip(GRIPPER_CLOSED)          # повторно затваряне преди повдигане
self._wait(0.3)
self._move('pre_grasp', PRE_GRASP, sec=5)   # повдигане
```

### Проблем 2: Обектът се плъзга при повдигане

**Симптом:** При повдигане обектът се плъзга в захвата и понякога пада.

**Причина:** Симулираното триене е достатъчно за статично задържане, но при
рязко движение инерцията на обекта надвишава захватната сила.

**Частично решение:** Повторна команда за захват + по-бавно повдигане (5 s).
Проблемът не е напълно елиминиран — зависи от физичните параметри на симулацията.

### Проблем 3: Несъответствие между итерации

**Симптом:** При повторно стартиране на симулацията, поведението леко се
различава (обектът може да е на малко различна позиция след рестарт).

**Причина:** Физичните симулатори имат малка недетерминираност поради
числената интеграция.

**Решение за тестване:** Ръчно нулиране на позицията на обекта преди всяко
изпитване:
```bash
gz service -s /world/mycobot_world/set_pose \
  --reqtype gz.msgs.Pose --reptype gz.msgs.Boolean --timeout 2000 \
  --req 'name: "cube", position: {x: 0.2620, y: -0.0842, z: 0.0300}, orientation: {x: 0, y: 0, z: 0.7071, w: 0.7071}'
```

## 8. Недостатъци и ограничения

### 8.1 Липса на преносимост

Всички стойности са специфични за:
- Точната позиция на обекта `(0.262, -0.084, 0.030)`
- Точния URDF модел на робота
- Точното начало на координатната система

**Последствие:** При преместване на обекта с 2 cm, захватът пропуска.
Необходимо е ново ръчно настройване.

### 8.2 Без контрол на крайния ефектор в декартово пространство

Не е известно точно къде е захватът в 3D пространство. Програмистът
работи само с ъгли, а не с метри.

```
Пример:
  Въпрос: "На колко сантиметра е захватът от пода?"
  Отговор с Подход A: Неизвестно без допълнително изчисление.
```

### 8.3 Без контрол на сблъсъците

Не се проверява дали ръката ще удари маса, стена или самата себе си.
При промяна на задачата съществува риск от сблъсък.

### 8.4 Трудна адаптация

| Задача | Усилие |
|--------|--------|
| Преместване на обекта с 5 cm | ~3-5 нови итерации |
| Нова целева позиция | ~5-8 нови итерации |
| Нов робот | Пълно пренастройване |
| Ново начало (поставяне) | ~4-6 нови итерации |

### 8.5 Бавен процес на разработка

Намирането на 4 точки изиска общо **~17 ръчни итерации** в симулацията.
Всяка итерация включва: промяна на стойност → стартиране → изчакване (~30 s)
→ наблюдение → нова корекция.

Общо приблизително прекарано време: **~2 часа** за настройка.
