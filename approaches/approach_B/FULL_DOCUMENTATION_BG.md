## 1. Основна идея

При Подход A позициите на робота се задаваха като ставни ъгли, намерени ръчно.
При Подход B позициите се задават като **координати в пространството** (x, y, z)
и математически алгоритъм — **Обратна кинематика (ОК)** — изчислява автоматично
необходимите ставни ъгли.

```
Аналогия:
  Подход A: Задавате колко да се огъне всеки пръст, за да хванете чаша.
  Подход B: Казвате "хвани чашата на тази позиция" — мозъкът изчислява
            сам как да огъне пръстите.
```

## 2. Математически основи

### 2.1 Права кинематика (Forward Kinematics — ПК)

**Въпрос:** При дадени ставни ъгли, къде е крайният ефектор?

```
ПК: [j1, j2, j3, j4, j5, j6] → (x, y, z)

Пример:
  Входни ъгли: [0.0, -0.815, -0.834, -0.169, 1.577, 0.0]
  Изходна позиция: (0.262, -0.084, 0.045) м
```

Изчислява се чрез **матрици на хомогенна трансформация**. Всяка става добавя
матрица на ротация и транслация:

```
T_total = T_base × T_j1 × T_j2 × T_j3 × T_j4 × T_j5 × T_j6 × T_tool

Където всяко T_ji = [R(θi) | d_i]   (4×4 матрица)
                    [0  0  0 | 1 ]

R(θi) = матрица на ротация около ставната ос под ъгъл θi
d_i   = вектор на транслация (дължина на звеното)
```

### 2.2 Обратна кинематика (Inverse Kinematics — ОК)

**Въпрос:** При дадена целева позиция (x, y, z), какви ставни ъгли са нужни?

```
ОК: (x, y, z) → [j1, j2, j3, j4, j5, j6]

Пример:
  Входна позиция: (0.262, -0.084, 0.045) м
  Изходни ъгли:  [0.0, -0.814, -0.833, -0.169, 1.576, 0.0] рад
```

ОК е **обратният проблем** и е много по-сложен от ПК. За 6-степенна ръка могат
да съществуват **множество решения** (или никакво).

```
Аналогия: ПК е като да питате "Ако движа ставата под ъгъл θ, крайната
точка ще е на (x,y,z)?" — директно изчисление.

ОК е като да питате "Как да движа ставите, за да достигна (x,y,z)?" —
трябва да разрешите система уравнения с 6 неизвестни.
```

### 2.3 Числени методи за ОК

Библиотеката **ikpy** използва **числен итеративен метод**:

```
1. Начална позиция: seed = приближени ставни ъгли
2. Изчисли ПК за seed → получаваш текуща позиция p_current
3. Изчисли грешка: error = target - p_current
4. Изчисли якобиан J (как позицията се промяна при малка промяна на ъглите)
5. Обнови ъглите: θ_new = θ_old + J⁻¹ × error
6. Повтаряй от стъпка 2 докато error < εпраг
```

**Защо са нужни "начални стойности" (seeds)?**

Числените методи намират **локален минимум** в близост до началната точка.
Ако началните стойности са далеч от правилното решение, алгоритъмът може
да намери грешна поза.

```
Решение в нашия случай:
  Използваме ставните ъгли от Подход A като начални стойности.
  Гарантираме, че ОК ще намери конфигурация с лакът нагоре —
  същата като при ръчно настроените ъгли.
```

## 3. URDF — описание на робота

### 3.1 Какво е URDF?

**URDF (Unified Robot Description Format)** е XML файл, описващ геометрията
и физическите свойства на робота. Съдържа:
- Дължини и ориентации на звената
- Позиции и типове на ставите
- Ставни ограничения (мин/макс ъгли, максимална скорост)
- Инерционни свойства (маса, моменти на инерция)

### 3.2 Кинематична верига (извлечена от URDF)

```
world (неподвижна точка)
  │
  ├─ world_to_base (фиксирана става)
  │       origin: [0, 0, 0]
  │
  ├─ joint2_to_joint1 (въртяща — ос Z)      j1
  │       origin: [0, 0, 0.1739]            ← 173.9 mm нагоре
  │       лимит:  [-2.93, +2.93] рад = ±167.8°
  │
  ├─ joint3_to_joint2 (въртяща — ос Y)      j2
  │       origin: [0, -0.08878, 0]          ← 88.78 mm встрани
  │       лимит:  [-2.35, +2.35] рад = ±134.6°
  │
  ├─ joint4_to_joint3 (въртяща — ос Y)      j3
  │       origin: [0.135, 0, -0.08878]      ← 135 mm напред
  │       лимит:  [-2.53, +2.53] рад = ±144.9°
  │
  ├─ joint5_to_joint4 (въртяща — ос Y)      j4
  │       origin: [0.120, 0, 0.08878]       ← 120 mm напред
  │       лимит:  [-2.53, +2.53] рад = ±144.9°
  │
  ├─ joint6_to_joint5 (въртяща — ос X)      j5
  │       origin: [0, -0.095, 0]            ← 95 mm встрани
  │       лимит:  [-2.93, +2.93] рад = ±167.8°
  │
  ├─ joint6output_to_joint6 (въртяща — ос Z) j6
  │       origin: [0, 0.0655, 0]            ← 65.5 mm
  │       лимит:  [-3.14, +3.14] рад = ±180°
  │
  ├─ joint6output_to_gripper_base (ФИКСИРАНА)
  │       origin: [0, -0.007, 0.056]        ← 56 mm до основата на захвата
  │
  └─ [разклоняващи се стави на захвата — ИЗКЛЮЧЕНИ от ОК верига]
```

### 3.3 Защо веригата се съкращава при j6?

```
Проблем: ikpy изисква линейна (неразклоняваща се) верига.
         Захватът има 2 пръста → 2 разклонения от j6.

Решение: Веригата се спира при joint6output_to_joint6.
         Позицията на "центъра на захвата" се задава чрез
         виртуален вектор (tool offset).

Код:
  stop_idx = next(i for i, l in enumerate(chain_full.links)
                  if l.name == 'joint6output_to_joint6')
  # chain се съкращава тук
```

## 4. Калибриране на отместването на инструмента

### 4.1 Защо е необходимо?

Началото на `link6` в URDF-а **не съвпада** с физическия център на захвата.
Ако не се добави корекция, ОК ще насочи `link6` към целевата точка, а не
захвата — и роботът ще е сантиметри встрани.

```
Без корекция:                С корекция:
  link6 → (0.262, -0.084, 0.045)   захват → (0.262, -0.084, 0.045)
  захват → (0.265, -0.081, 0.189)  link6 → (изчислено автоматично)
              ↑ ГРЕШНО                         ↑ ПРАВИЛНО
```

### 4.2 Процедура по калибриране (стъпка по стъпка)

**Стъпка 1:** Вземане на ставните ъгли от Подход A при GRASP като еталон

```python
joints_A = [0.0, -0.815, -0.834, -0.169, 1.577, 0.0]
# Знаем, че при тези ъгли захватът е при (0.262, -0.084, 0.045)
```

**Стъпка 2:** Изграждане на ОК верига БЕЗ отместване

```python
chain = ikpy.chain.Chain.from_urdf_file(
    urdf_path,
    base_elements=['world'],
    last_link_vector=[0, 0, 0]   # без отместване
)
```

**Стъпка 3:** Изчисляване на ПК — намиране на позицията на link6

```python
# Разширен вектор на ставни ъгли (включва пасивни звена)
full_joints = [0] * len(chain.links)
for i, name in enumerate(arm_joint_names):
    idx = chain_index[name]
    full_joints[idx] = joints_A[i]

fk_matrix = chain.forward_kinematics(full_joints)
link6_pos = fk_matrix[:3, 3]   # последните 3 елемента на 4-та колона
# link6_pos ≈ [0.2652, 0.0809, 0.099] (примерни стойности)
```

**Стъпка 4:** Изчисляване на отместването

```python
target_pos = [0.2620, -0.0842, 0.045]   # известна позиция на захвата

offset = [target_pos[0] - link6_pos[0],   # dx
          target_pos[1] - link6_pos[1],   # dy
          target_pos[2] - link6_pos[2]]   # dz

# offset ≈ [-0.0032, -0.0033, 0.144]
```

**Интерпретация:**
```
dz = 0.144 m = 144 mm
  Захватът е 144 mm "пред" link6 по локалната Z-ос.
  Това е физическата дължина от центъра на link6 до точката на захвата.

dx = -0.0032 m = -3.2 mm  (малко встрани)
dy = -0.0033 m = -3.3 mm  (малко встрани)
  Малки корекции поради механичен монтаж на захвата.
```

**Стъпка 5:** Верификация

```python
chain_calibrated = ikpy.chain.Chain.from_urdf_file(
    urdf_path,
    last_link_vector=[-0.0032, -0.0033, 0.144]  # с корекция
)
fk_calibrated = chain_calibrated.forward_kinematics(full_joints)
calibrated_pos = fk_calibrated[:3, 3]

error = sqrt((calibrated_pos - target_pos)²)
# error = 0.0 mm ✓ — перфектно съвпадение
```

## 5. Решаване на ОК за всяка точка

### 5.1 PRE_GRASP

```
Целева позиция: (0.262, -0.084, 0.120)

Изчисление на Z:
  Z_куб_центъра + просвет = 0.030 + 0.090 = 0.120 m

ОК решаване с начална стойност = Подход A PRE_GRASP ъгли:
  [0.0, -0.705, -0.7237, -0.169, 1.5772, 0.0]

Намерено решение:
  [0.000, -0.703, -0.722, -0.169, 1.576, 0.0]

Сравнение с Подход A:
  j2: -0.703 vs -0.705 → разлика 0.002 рад = 0.11°
  j3: -0.722 vs -0.724 → разлика 0.002 рад = 0.11°
  Останалите: практически идентични
```

### 5.2 GRASP

```
Целева позиция: (0.262, -0.084, 0.045)

Изчисление на Z:
  Z_куб_центъра + 0.015 = 0.030 + 0.015 = 0.045 m
  (0.015 m = половината от ширината на куба по X = 40mm/2 = 20mm, но
   коригирано за реалната позиция на пръстите)

ОК решаване с начална стойност = Подход A GRASP ъгли:
  [0.0, -0.815, -0.834, -0.169, 1.577, 0.0]

Намерено решение:
  [0.000, -0.814, -0.833, -0.169, 1.576, 0.0]

Сравнение с Подход A:
  j2: -0.814 vs -0.815 → разлика 0.001 рад = 0.057°
  j3: -0.833 vs -0.834 → разлика 0.001 рад = 0.057°
  ← Практически идентично! ОК потвърждава ръчните стойности.
```

### 5.3 LIFT

```
Целева позиция: (0.262, -0.084, 0.150)

Изчисление на Z:
  0.030 + 0.120 = 0.150 m (12 cm над центъра на куба)
  (достатъчно за изчистване над масата и страничните стени)

Намерено решение:
  [0.000, -0.706, -0.714, -0.157, 1.571, 0.0]

Забележка: j4 = -0.157 (vs -0.169 при PRE_GRASP)
  Различно — на по-голяма Z-височина геометрията е различна
  и j4 се адаптира автоматично.
```

## 6. Предимства на ОК подхода

### 6.1 Интуитивно задаване на позиции

```
Подход A: "j2 = -0.815, j3 = -0.834 ..." — няма физическо значение
Подход B: "захватът да е на (0.262, -0.084, 0.045)" — ясна геометрия
```

### 6.2 Лесна адаптация

Ако кубът е на нова позиция `(0.300, -0.050, 0.030)`:

```python
# Подход A: пренастройва се ВСИЧКО ръчно (часове)

# Подход B: само 3 числа:
CUBE_X, CUBE_Y, CUBE_Z = 0.300, -0.050, 0.030
# Всички waypoints се преизчисляват автоматично!
```

### 6.3 Проверима точност

```
Подход A: не знаем точно колко грешим (само визуална оценка)
Подход B: ОК грешката е измерима:
  pre_grasp: 0.2 mm (при идеален URDF)
  grasp:     0.0 mm (calibrated)
```

## 7. Недостатъци и ограничения

### 7.1 Изисква точен URDF

Ако URDF не съответства точно на реалния/симулирания робот:

```
Грешка в дължина на звено ±1 mm → Грешка в крайна позиция ~2-5 mm
```

В реална система (не симулация) калибрирането е по-сложно и може
да изисква специализирано оборудване.

### 7.2 Без гаранция за намиране на решение

Ако целевата позиция е:
- Извън работното пространство на робота
- Близо до сингулярност (вж. 7.3)
- При изчерпани ставни лимити

→ ОК може да не намери решение или да намери грешна поза.

### 7.3 Сингулярности

**Сингулярност** е позиция, при която роботът губи 1 или повече степени
на свобода — малка промяна в позицията на захвата изисква много голяма
промяна на ставен ъгъл.

```
Пример: Напълно изпъната ръка (всички звена по права линия).
        При такава поза движение на захвата встрани изисква
        завъртане на основата j1 с много голям ъгъл.
```

В нашата задача сингулярностите са избегнати — роботът работи
в удобна конфигурация далеч от пълно изпъване.

### 7.4 Числена грешка

ОК решателят е итеративен и може да не намери точното решение:
- При лоша начална стойност: може да намери погрешна конфигурация
- При близки множество решения: може да се "колебае" между тях

```
Measured error в нашия случай: < 0.2 mm (приемливо)
```

### 7.5 Ориентация на захвата

В текущата имплементация ОК решава само **позицията** (x, y, z),
но не и **ориентацията** (посоката на захвата).

```python
chain.inverse_kinematics(
    target_position = [x, y, z],
    orientation_mode = None,   # ← само позиция, без ориентация
)
```

Ориентацията се контролира косвено чрез j6 = 0.0 (принудително).
Пълен контрол на ориентацията би изисквал `orientation_mode='all'`
и задаване на матрица на ротация.

### 7.6 Зависимост от Python библиотека

```
pip install ikpy
```

Реалните роботни системи използват по-надеждни ОК решатели
(напр. KDL, TRAC-IK), но те изискват допълнителна конфигурация.
